  Add task-specific tools to the same call when the task obviously needs them:
  read_console_messages / read_network_requests for debugging, form_input for
  forms, gif_creator for recordings, javascript_tool for page scripting.

  ## GIF recording

  When performing multi-step browser interactions that the user may want to
  review or share, use mcp__claude-in-chrome__gif_creator to record them.

  You must ALWAYS:
  * Capture extra frames before and after taking actions to ensure smooth
  playback
  * Name the file meaningfully to help the user identify it later (e.g.,
  "login_process.gif")

  ## Console log debugging

  You can use mcp__claude-in-chrome__read_console_messages to read console
  output. Console output may be verbose. If you are looking for specific log
  entries, use the 'pattern' parameter with a regex-compatible pattern. This
  filters results efficiently and avoids overwhelming output. For example, use
  pattern: "[MyApp]" to filter for application-specific logs rather than
  reading all console output.

  ## Alerts and dialogs

  IMPORTANT: Do not trigger JavaScript alerts, confirms, prompts, or browser
  modal dialogs through your actions. These browser dialogs block all further
  browser events and will prevent the extension from receiving any subsequent
  commands. Instead, when possible, use console.log for debugging and then use
  the mcp__claude-in-chrome__read_console_messages tool to read those log
  messages. If a page has dialog-triggering elements:
  1. Avoid clicking buttons or links that may trigger alerts (e.g., "Delete"
  buttons with confirmation dialogs)
  2. If you must interact with such elements, warn the user first that this may
  interrupt the session
  3. Use mcp__claude-in-chrome__javascript_tool to check for and dismiss any
  existing dialogs before proceeding

  If you accidentally trigger a dialog and lose responsiveness, inform the user
  they need to manually dismiss it in the browser.

  ## Avoid rabbit holes and loops

  When using browser automation tools, stay focused on the specific task. If
  you encounter any of the following, stop and ask the user for guidance:
  - Unexpected complexity or tangential browser exploration
  - Browser tool calls failing or returning errors after 2-3 attempts
  - No response from the browser extension
  - Page elements not responding to clicks or input
  - Pages not loading or timing out
  - Unable to complete the browser task despite multiple approaches

  Explain what you attempted, what went wrong, and ask how the user would like
  to proceed. Do not keep retrying the same failing browser action or explore
  unrelated pages without checking in first.

  ## Tab context and session startup

  IMPORTANT: At the start of each browser automation session, call
  mcp__claude-in-chrome__tabs_context_mcp first to get information about the
  user's current browser tabs. Use this context to understand what the user
  might want to work with before creating new tabs.

  Never reuse tab IDs from a previous/other session. Follow these guidelines:
  1. Only reuse an existing tab if the user explicitly asks to work with it
  2. Otherwise, create a new tab with mcp__claude-in-chrome__tabs_create_mcp
  3. If a tool returns an error indicating the tab doesn't exist or is invalid,
  call tabs_context_mcp to get fresh tab IDs
  4. When a tab is closed by the user or a navigation error occurs, call
  tabs_context_mcp to see what tabs are available</browser_instruction>

  1. Purpose

  Meeting notes pile up as markdown. Action items get lost and follow-ups are
  late or never sent. actiontrack extracts action items from the notes, tracks
  their status, and drafts follow-up emails as Gmail drafts for a human to
  review. It never sends.

  2. Functional requirements

  FR-1 ingest <folder>
  - Parse every .md note in the folder and ignore other file types.
  - Extract the meeting date, the attendees, and each action item (owner, task,
    due date, source file, status).
  - Resolve relative due dates ("by Friday", "mid-October") to real dates, using
    the meeting date as the anchor.
  - Dedupe items repeated across meetings.
  - Re-running ingest must be idempotent. It must not create duplicates or reset
    items already marked done.
  - Print a summary: files parsed, items added, items skipped as duplicates, and
    notes skipped as malformed with the reason for each.

  FR-2 list
  - Filters: --owner, --status open|done|overdue, --due-before <date>. They can
    be combined.
  - Overdue means open and due before today. It is computed at read time, not
    stored.
  - Output columns: id, owner, task, due, status, source file.
  - Items with no owner or no due date still appear, clearly labelled.

  FR-3 done <id>
  - Marks the item done. An unknown id gives a clear error.
  - Marking an already-done item is a no-op with a message.

  FR-4 followup <owner>
  - Builds one email per owner covering their open and overdue items, with
    overdue items listed first.
  - Creates a Gmail draft through the Gmail MCP connector. It never sends.
  - If the owner is ambiguous or has no email address, it stops with a clear
    message.

  Non-functional
  - Malformed notes never crash the tool.
  - State persists locally between commands.
  - Errors are clear and exit codes are meaningful.
  - Behaviour is deterministic and testable. "Today" is injectable for tests.

  3. Edge-case rules (proposed defaults)

  Case: Duplicates
  Proposed behaviour: Normalise the task text (case, punctuation, due
    phrasing). Items with the same owner and a matching task are one item,
    linked to all source meetings. Keep the earliest as the original and
    record the later ones as "seen again".
  ────────────────────────────────────────
  Case: No owner
  Proposed behaviour: Store as UNASSIGNED. Show it in list. It gets no
    follow-up email, but is flagged in the ingest report.
  ────────────────────────────────────────
  Case: No due date
  Proposed behaviour: Store with a null due date. It is never overdue. Show
    "no date".
  ────────────────────────────────────────
  Case: Same first name
  Proposed behaviour: Resolve to a full name using that meeting's attendee
    list. If exactly one match, use it. If several match, mark the owner
    ambiguous and don't guess.
  ────────────────────────────────────────
  Case: Malformed note
  Proposed behaviour: Skip it, report the filename and reason, and continue.

  4. What the sample data shows

  - Duplicate items: items recur across the weekly series, and the same task is
    often worded differently.
  - Done checkboxes: - [x] and - [X] appear, so done-state is read from the
    source, and re-ingest must not overwrite local status.
  - Other formats: items also appear as * [ ], + [ ], nested sub-items, a
    markdown table, and ACTION: lines, in addition to - [ ].
  - Date formats: frontmatter-style date: and attendees: [..] variants appear.
    Dates come as 9 September 2026, Monday, 14 September 2026, and sometime last
    week.
  - Due-date phrasing: "by Friday", "Oct 3rd", "15 October", "7 Oct",
    "mid-October", "EOD", "tomorrow", "from 9 Oct".
  - Ambiguous owners: "Priya" (Nair or Shah), "Rahul" (Mehta or Verma), "Priya
    N.", "Everyone", and one note with no names at all.
  - Non-notes and junk:

    - untitled.md has no header, date or attendees.
    - 2026-09-09-notes-final-v2.md is empty.
    - A .txt draft contains a checkbox but isn't a meeting note.

  5. Scenarios (acceptance tests)

  1. Happy path: ingest the folder. The summary shows 30+ files, N items, and
     the malformed notes skipped with reasons. Exit code is 0.
  2. Idempotent re-ingest: ingest, run done 5, ingest again. There are no new
     duplicates and item 5 is still done.
  3. Relative date: "Priya to send the quote by Friday" in a note dated
     2026-09-01 (a Tuesday) becomes due 2026-09-04.
  4. Overdue: with today = 2026-11-24, any open item due before that shows as
     overdue. A done item with a past due date does not.
  5. Combined filter: list --owner "Karan Joshi" --status overdue --due-before
     2026-10-15 returns only the matching items.
  6. Duplicate merge: the same quote task appears in three weekly notes with
     different wording. It shows once, with all three sources.
  7. Ambiguous name: the offsite note's "Priya to own the hiring plan" is
     flagged ambiguous. Both Priyas were present, so it isn't guessed. In the
     go/no-go note, "Priya N." resolves to Priya Nair.
  8. No owner or no date: the item is listed, labelled, and excluded from
     follow-ups. It is mentioned in the ingest report.
  9. Malformed notes: the empty file, the binary scratch.md, untitled.md, and
     the non-notes are skipped and reported. The other files are still
     processed.
  10. Follow-up: followup "Karan Joshi" creates one Gmail draft with overdue
      items first, then open ones. Nothing is sent. The tool prints a
      confirmation with the draft id.
  11. Follow-up failure: if the Gmail connector is unauthorised or unavailable,
      it exits with a clear message and makes no partial side effects.
  12. Bad input: done 9999 gives "no such item". followup "Priya" lists the
      matching Priyas and asks the user to pick one.

  6. Open questions

  Tooling
  1. Language and runtime? Python or Node/TypeScript? I'd suggest Python with
     argparse or click.
  2. Storage? SQLite or a JSON file? I'd suggest SQLite, stored in .actiontrack/
     next to the notes or in the user's home directory.
  3. Gmail integration: the Gmail connector in this session needs authorising
     before drafts can be created. For the CLI itself, how should it reach the
     Gmail MCP connector? Options are an MCP client from the CLI, or the CLI
     emits the email and I create the draft through the session. Which do you
     want?

  Behaviour
  4. Email addresses: where do they come from? The notes only have names. Should
  I use a people.json mapping, or draft with the To field blank?
  5. "Today": use the real system date (2026-11-24), which makes nearly
  everything overdue, or a --today override for demos?
  6. Dedupe strictness: is fuzzy matching acceptable (for example "send the
  revised quote to Acme" equals "send Acme the revised quote")? If so, what is
  the risk tolerance for wrongly merging items?
  7. Status conflicts: if a later note shows [x] for an item still open locally
  (or the reverse), should the note win or the local state?
  8. Unparseable dates: "sometime last week" as a meeting date. Skip the whole
  note, or fall back to the filename date? I'd suggest the filename date,
  flagged as a warning.
  9. Unresolvable due dates: "mid-October" and "EOD". Should I use a fixed rule
  (for example mid-October = the 15th, EOD = the meeting date), or store them as
  no date?
  10. "Everyone to submit goals": expand to one item per attendee, store as
  owner "Everyone", or treat it as unowned?
  11. Items outside a checklist: should I also parse table rows and ACTION:
  lines, or only - [ ] style checkboxes as the brief says? I'd suggest parsing
  all of them.
  12. Ids: short integers (easy to type) are fine, but are they stable across
  re-ingest? I'd suggest a stable assigned id that is never reused.
  13. Follow-up content: include the source meeting and its date for each item?
  Any required tone or template? Should followup accept --all?
  14. Overdue grace: is "due today" overdue, or only strictly past?

  My recommended defaults are SQLite, Python, today's date overridable with
  --today, and a people.json for emails. Answer whichever of these you care
  about, and I'll take the rest as proposed.
